= Kubeflow Ingestion Pipeline
:navtitle: Kubeflow Pipeline

The RAG quickstart ingests documents through an `ingestion-pipeline` REST API service, backed by a Kubeflow Data Science Pipelines Application (DSPA) that does the actual fetch/chunk/embed/store work.
Every one of FantaCo's five pre-loaded document categories, HR, Legal, Procurement, Sales, and TechSupport, was ingested this way automatically when your environment was provisioned.
The same API is what the *Upload Documents* button in the chat UI calls behind the scenes; see xref:03-knowledge-base.adoc[Knowledge Base] for that flow.

== What the pipeline does

Ingesting a document set is a multi-step workflow:

. *Fetch*: source documents are pulled from the configured source, either a GitHub repository (used for the built-in FantaCo categories) or an S3-compatible bucket in MinIO (used for documents you upload yourself).
. *Clean*: raw text is extracted from each file. PDFs are parsed page by page; plain text and Markdown files are read directly.
. *Chunk*: the cleaned text is split into overlapping chunks so that context is not lost at chunk boundaries.
. *Embed*: each chunk is passed through the configured embedding model (default: `all-MiniLM-L6-v2`) to produce a fixed-length vector representation.
. *Store*: the chunk text and its embedding vector are written into PostgreSQL + pgvector under the target vector store name. The collection is created if it does not already exist.

Once a pipeline completes, its chunks are immediately available for semantic search in both Chat and Agent modes.

== How the built-in categories were ingested

At deploy time, one Kubernetes Job per category POSTs a pipeline definition to the ingestion-pipeline API, pointing it at that category's folder in the `rh-ai-quickstart/RAG` GitHub repository:

[cols="1,2",options="header"]
|===
|Job |Vector store created

|`add-hr-pipeline-pipeline`
|`hr-vector-db-v1-0`

|`add-legal-pipeline-pipeline`
|`legal-vector-db-v1-0`

|`add-procurement-pipeline-pipeline`
|`procurement-vector-db-v1-0`

|`add-sales-pipeline-pipeline`
|`sales-vector-db-v1-0`

|`add-techsupport-pipeline-pipeline`
|`techsupport-vector-db-v1-0`
|===

Check their status from the Bastion terminal:

[source,bash,role="execute",subs=attributes+]
----
oc get jobs -l app.kubernetes.io/name=ingestion-pipeline -n {user}-rag
----

Each `Job` stays `Running` until its `wait-for-pipeline` init container confirms the ingestion-pipeline API is reachable, then it posts the request and completes. The actual chunk/embed/store work happens asynchronously afterward, executed by the Data Science Pipelines Application control plane:

[source,bash,role="execute",subs=attributes+]
----
oc get pods -l component=data-science-pipelines -n {user}-rag
----

== Adding your own document set

To ingest a new document set beyond the five pre-loaded categories, call the ingestion-pipeline API's `/add` endpoint directly with a source definition. First, find the service (its name is prefixed with your environment's release name):

[source,bash,role="execute",subs=attributes+]
----
oc get svc -l app.kubernetes.io/name=ingestion-pipeline -n {user}-rag
----

Then, from the Bastion terminal, POST a pipeline definition. This example ingests documents from the `llama` bucket in MinIO (the same bucket and credentials the *Upload Documents* UI flow uses), replacing `<ingestion-pipeline-service>` with the name from the previous command:

[source,bash,subs=attributes+]
----
curl -sX POST http://<ingestion-pipeline-service>/add \
  -H 'Content-Type: application/json' \
  -d '{
    "name": "my-custom-vector-db",
    "vector_store_name": "my-custom-vector-db-v1-0",
    "version": "1.0",
    "embedding_model": "all-MiniLM-L6-v2",
    "source": "S3",
    "S3": {
      "access_key_id": "minio_rag_user",
      "secret_access_key": "minio_rag_password",
      "bucket_name": "llama",
      "endpoint_url": "http://minio.{user}-rag.svc.cluster.local:9000",
      "region": "us-east-1"
    }
  }'
----

[NOTE]
====
`<ingestion-pipeline-service>` is a literal placeholder here, replace it with the real service name before running the command; this block intentionally omits the copy-button role for that reason.
====

== Verifying ingestion

Once a pipeline run completes, confirm that chunks were written to pgvector by querying the knowledge base.
Switch to the Streamlit UI, select the vector store you ingested into, and ask a question whose answer appears in one of the source documents.

For a deeper check of retrieval quality, see xref:06-querying-knowledge-base.adoc[Querying the Knowledge Base].

== Troubleshooting

[cols="2,3",options="header"]
|===
|Symptom |Action

|`add-<category>-pipeline-pipeline` Job stuck `Running` with `0/1` completions
|Check the ingestion-pipeline pod is `Running` and its service exists: `oc get pods,svc -l app.kubernetes.io/name=ingestion-pipeline -n {user}-rag`. The Job's `wait-for-pipeline` init container polls that service and cannot proceed without it.

|`ConnectionRefused` calling `/add`
|Verify the ingestion-pipeline service name and that you're running the `curl` from inside the cluster (the Bastion terminal), not from your local machine.

|Run completes but no results appear in chat
|Confirm the `vector_store_name` you ingested into matches exactly what is selected in the UI Knowledge Base dropdown.

|Poor retrieval quality after ingestion
|Try a smaller chunk size and re-running the pipeline so chunks are more granular.

|PDF pages appear garbled or empty
|Scanned PDFs require OCR pre-processing before ingestion. Convert them to text-layer PDFs first.
|===
